# v7.4 validation-first upgrade plan

This upgrade deliberately avoids drawing market/sector rules from a few failed
selection days.  The goal is to make the selector improvable without leaking
review data into production or overfitting tiny samples.

## What is locked

- `auction_change_pct` / `竞价涨幅` is the premarket auction-cost concept.
- `latest_change_pct` can be a post-close / latest quote field in review flows;
  it must not be treated as proof of production leakage without code-path and
  timestamp verification.
- `close_pct`, `excess_return`, dailyline OHLC fields, and flat review files are
  review-only.
- A few days of real selections are failure cases, not enough evidence to create
  board/sector laws.

## New tools

### 1. Field-lineage audit

```bash
python scripts/audit_duanxianxia_field_lineage.py \
  --analysis projects/duanxianxia/reports/2026-05-21/premarket/221500_analysis_v7_3_durable_v2.json \
  --json
```

Use it before changing selector logic.  It reports:

- production-like fields visible in candidate rows;
- review-only fields present after backfill;
- ambiguous price names that need schema/timestamp verification;
- concrete examples by code and row source.

The audit is intentionally a boundary report, not an automatic leak verdict.

### 2. Validation-first selector evaluation

```bash
python scripts/evaluate_duanxianxia_selector.py \
  --analysis-glob 'projects/duanxianxia/reports/*/premarket/*analysis_v7_3*.json' \
  --min-sample 30 \
  --output-json projects/duanxianxia/reports/selector_validation.json \
  --output-md projects/duanxianxia/reports/selector_validation.md
```

It measures by action bucket / setup / durable pattern:

- count and with-performance count;
- hit rate on excess return;
- average / median excess return;
- average win, average loss, payoff ratio;
- tail-loss rate `<= -3%`;
- big-win rate `>= 5%`;
- false positives and missed winners.

Buckets below `--min-sample` are marked `exploratory_only`.  They can generate
hypotheses, but should not directly change production thresholds.

## Correct improvement loop

1. Run field-lineage audit on the analysis file being reviewed.
2. Run validation evaluation across all available historical analysis files.
3. Only consider a production rule if one of these is true:
   - it fixes a data-contract / field-lineage bug;
   - it improves a bucket with enough sample size;
   - it is a risk-control invariant that does not depend on a small sample.
4. Turn every proposed selector change into an explicit hypothesis:
   - feature involved;
   - expected mechanism;
   - train dates / validation dates;
   - expected effect on hit rate, payoff ratio, tail-loss rate, and missed winners.
5. Keep review metrics out of production code.  Review scripts may attach them
   under `derived_performance` / `performance`, but selector branches must not
   inspect realized close or excess fields.

## What not to do

- Do not infer that a board, exchange segment, or sector is structurally bad from
  one or two dates.
- Do not create a hard ban just because it would have avoided a recent loser.
- Do not promote a watch/reject winner into BUY logic unless it survives a wider
  walk-forward sample.
- Do not mix a display rank with an executable action rank.

## Practical next selector work

The next production selector change should be done only after a validation report
exists.  Good candidates for mechanism-level work are:

1. **Decision/ranking separation**: keep BUY/WATCH/REJECT as policy decisions;
   evaluate expected-return rank separately.
2. **Redundancy control**: measure whether multiple signals are independent or
   simply counting the same auction evidence twice.
3. **Payoff-aware review**: optimize average excess and tail loss together, not
   hit rate alone.
4. **Missed-winner taxonomy**: classify missed winners by signal family and only
   promote families that repeat across enough dates.
5. **Position sizing / confidence**: if a signal is useful but volatile, express
   it as lower confidence rather than binary exclusion.
